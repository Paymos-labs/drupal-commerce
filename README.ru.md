## Требования

Нужны Drupal `^10.3 || ^11` и Drupal Commerce `^3`. Модуль требует PHP `^8.1`, но ваша версия Drupal может требовать более свежий PHP — ориентируйтесь на более строгое ограничение. Магазину нужен публичный HTTPS-адрес для подключения и приёма платёжных уведомлений.

Модуль распространяется под лицензией GPL-2.0-or-later. Его зависимость `paymos/php-sdk` выходит под лицензией MIT и требует версию `^1.12.0` (`1.12.0` или более новый совместимый релиз ветки `1.x`), чтобы передавать нормализованный массив `products[]` на чекауте через `Paymos\Plugin\InvoicePresentation::normalizeProducts`.

## Установка модуля

Установите стабильный релиз через Composer, чтобы автоматически подтянуть `paymos/php-sdk:^1.12.0`:

```sh
composer require 'drupal/commerce_paymos:^1.0'
```

Можно поставить и отдельный ZIP-архив для ручной установки: распакуйте каталог `commerce_paymos` в папку дополнительных модулей сайта (contributed modules). Архив уже содержит `paymos/php-sdk` `1.11.0` в каталоге `vendor/` (`SdkBootstrap` подключит его, если класс `Paymos\Client` ещё не загружен автозагрузчиком), поэтому не разделяйте встроенные файлы. После установки включите модуль Paymos в Drupal.

Если на сайте вместе с ручным ZIP-архивом уже глобально загружена более старая версия `paymos/php-sdk` из другого Composer-пакета, `CheckoutService` проверит `method_exists(InvoicePresentation::class, 'normalizeProducts')` и без сбоя переключится на счёт только с суммой (`amount-only`), не ломая оформление заказа.

После обновления модуля сбросьте кэш Drupal: `drush --uri=https://your-store.example cache:rebuild`.

## Подключение магазина

Откройте `/admin/commerce/config/payment/paymos` в Drupal. В кабинете Paymos выберите проект для этого магазина. Нажмите **Connect Paymos** в Drupal, подтвердите подключение и вернитесь в Drupal, чтобы нажать **Check approval**.

Затем откройте `/admin/commerce/config/payment-gateways/add`. Создайте платёжный шлюз, выберите Paymos и укажите нужную среду — Sandbox или Live. Подключение аккаунта и создание шлюза Commerce — два отдельных шага; выполните оба, прежде чем включать оплату на витрине.

Скопируйте адреса возврата из админки Drupal в свой проект Paymos: `/paymos/return` в поле Success URL и `/paymos/return?cancel=1` в поле Fail URL. Это делается один раз. Страница оплаты Paymos использует эти адреса для ссылки **Back to store**. Drupal хранит стандартные адреса возврата последнего заказа в браузерной сессии покупателя один час: в другом браузере, после истечения сессии или при смене привязки заказа/шлюза покупатель попадёт на главную страницу магазина. Возврат в браузер никогда не подтверждает оплату — статус определяют только проверенные вебхуки, запросы к API и запись платежа в Commerce. При создании счёта передаются лишь ссылка на заказ, `project_id`, `amount`, `currency` и опциональный нормализованный массив `products[]` без персональных данных покупателя.

Учётные данные лежат в зашифрованном состоянии Drupal (Drupal state). Шифрование опирается на приватный ключ Drupal и `hash_salt`, поэтому секреты не попадают в экспорт конфигурации. Если канонический URL магазина изменился, подключите магазин к Paymos повторно.

## Позиции заказа и границы каталога

Когда доступен метод `Paymos\Plugin\InvoicePresentation::normalizeProducts`, `CheckoutService` отсеивает строки доставки, скидок, налогов, сборов и примечаний и нормализует `1..50` товарных позиций (`title`, целое положительное `quantity`, десятичную строку `unit_amount` и опциональное текстовое `description`) в массив `products[]` по правилу «всё или ничего»: если хотя бы одна позиция некорректна или в корзине больше `50` товаров, Drupal отправляет счёт `amount-only` с итоговой суммой заказа (`amount`) вместо обрезанного списка. Пустые описания опускаются у конкретной позиции, сама позиция сохраняется. Нормализованный снимок `products[]` фиксируется в `InvoiceStore`, чтобы повторная попытка после обрыва создания счёта отправляла те же значения, а не изменившийся заказ. Для старых снимков при повторе из исходящей копии убирается только устаревший ключ `image_url`, остальные поля не меняются, а сохранённый снимок остаётся нетронутым.

Во всём каталоге из 12 CMS-плагинов Paymos (`plugins/cms-store-catalog.json`):

- Все **11** товарных CMS-плагинов передают `products[]`: **10** PHP-плагинов на базе `Paymos\Plugin\InvoicePresentation::normalizeProducts` (`WooCommerce`, `Easy Digital Downloads`, `Drupal Commerce` на `paymos/php-sdk:^1.12.0`, `OpenCart`, `PrestaShop`, `WHMCS`, `CS-Cart`, `Magento 2`, `Shopware 6` и `HikaShop` `1.1.0` на `^1.11.0`) плюс **Odoo** (`20.0.1.1.0`, который передаёт `products` через встроенный Paymos Python SDK `1.x` (`>= 1.6.0`) вызовом `client.request("POST", "/v1/invoices", payload)`).
- Только шлюз пожертвований **`givewp-paymos`** работает в режиме `amount-only`, потому что у пожертвований нет корзины товаров.

## Регулярные проверки платежей

Настройте запуск Drupal cron с каноническим HTTPS-адресом магазина. Например:

```sh
drush --uri=https://your-store.example cron
```

Cron проверяет незавершённые платежи ограниченными пакетами. Не отключайте его даже при стабильной доставке вебхуков, чтобы зависшие операции продолжали сверяться.

## Как поступает оплата по заказам

Уведомления о платежах приходят с подписью и запускают проверку через API. Перед записью платежа счёт обязан совпасть с заказом, проектом Paymos, средой, суммой и валютой. Нативная SQL-транзакция фиксирует один завершённый платёж Commerce — дублирующие уведомления не создают повторных записей.

Частичные или просроченные платежи не открывают отгрузку автоматически. Платёж с расхождением в реквизитах требует ручной проверки. Исполнением заказов управляет рабочий процесс вашего магазина в Drupal Commerce, поэтому при настройке шлюза проверьте его правила.

## Возвраты

Модуль поддерживает нативные возвраты через Paymos Merchant API (`/v1/refunds`) в двух режимах, где сумму рассчитывает сервер: `full` (полный возврат по счёту) и `overpayment` (возврат переплаты по счёту `paid_over`). Paymos отправляет средства новой исходящей транзакцией в блокчейне строго на проверенный адрес `first_sender`, зафиксированный при оплате счёта: вручную кошелёк получателя не вводится, а произвольные частичные возвраты не поддерживаются.

Администраторы с нужными правами запускают и отслеживают возвраты из двух защищённых разделов Drupal:

- форма операции **Refund** на вкладке **Payments** заказа (`RefundForm`), где можно выбрать **Full refund** (`full`) или **Refund overpayment** (`overpayment`);
- панель **Paymos refunds** на странице `/admin/commerce/config/payment/paymos` (`ConnectForm`), где можно запускать возвраты `full` и `overpayment` для подходящих платежей Paymos и видеть статусы операций и внешние возвраты.

Подписанные вебхуки на `/paymos/webhook` и сверка через Drupal cron обновляют ожидающие возвраты и переводят платёж Commerce в статус возвращённого после того, как Paymos подтвердит завершение (`completed`). В режиме Sandbox финальные исходы возврата (`completed`, `failed`, `cancelled`) можно симулировать для проверки.

## Удаление модуля

Отключить Paymos на `/admin/commerce/config/payment/paymos` нельзя, пока по магазину есть записи в истории возвратов. Удалить модуль нельзя, пока в базе есть записи о возвратах или незавершённые ожидающие платежи Paymos (завершённые счета и строки событий вебхуков отключению и удалению не мешают). Когда блокирующих записей нет, удаление стирает зашифрованные учётные данные модуля и оставляет стандартные записи платежей Drupal Commerce.
